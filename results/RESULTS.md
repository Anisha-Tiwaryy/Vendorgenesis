# VendorGenesis results

Data: **synthetic base**. Generated by `python evaluate.py`; every number below is measured.

## Input

- 3,000 true vendors spread across 3 legacy systems as **4,848 vendor records**; 45.8% of vendors appear more than once.
- 39,802 AP invoices over 12 months, including 527 planted duplicate payments.

| IFSC valid | 0.897 |

## Blocking

- Candidate pairs: **56,047** of 11,749,128 possible (reduction ratio 99.52%).
- Pair completeness: **98.7%** of true duplicate pairs survive blocking (the recall ceiling for everything after).
- New pairs contributed by each key: {'pincode+first_token': 15671, 'first_two_tokens': 40163, 'pan': 129, 'phone': 84}; oversized blocks skipped: 0.

## Scale: why rules that work on a sample fail on the full vendor master

More vendors means more near-namesakes (same prefix, same locality, different business). Fuzzy-name rules merge them; the model uses PAN, bank and address evidence instead.

| true vendors | legacy records | best rule F1 | best rule false merges | Gradient Boosting F1 | GB false merges |
|---|---|---|---|---|---|
| 500 | 826 | 0.9247 | 51 | 0.9902 | 1 |
| 1,000 | 1,624 | 0.8629 | 214 | 0.9929 | 4 |
| 2,000 | 3,230 | 0.7252 | 1,077 | 0.9964 | 5 |
| 3,000 | 4,848 | 0.7007 | 2,576 | 0.9967 | 9 |

## Duplicate payments

Same check (same amount, same invoice sequence number, within 45 days), run per legacy record vs per deduplicated vendor:

| check runs per | planted_duplicates | planted_value | caught | caught_value | flags_raised | false_flags |
|---|---|---|---|---|---|---|
| legacy vendor record | 527 | Rs 5.94 crore | 0 | Rs 0 | 0 | 0 |
| deduplicated vendor (VendorGenesis) | 527 | Rs 5.94 crore | 518 | Rs 5.78 crore | 519 | 1 |

Deduplication exposes **518 of 527** planted duplicate payments (Rs 5.78 crore of Rs 5.94 crore) with 1 false flag(s). The duplicate-payment rate is an assumption of the simulation (3% of invoices for duplicated vendors), so read the rupee figure as the mechanism's size in this scenario, not a real-world estimate.
